# 语音识别与手势识别：昇腾 `.om` 模型调研

更新：2026-10-16。调研目标：为需求规格中的 **E1 手势+表情交互**、**E7 语音控制** 找到能在本机 Atlas 200I DK A2（芯片 `Ascend310B1`，CANN 6.2.RC1，内存 3.5 GB）上**直接运行或可重转**的 `.om` 模型。

沿用[工作区总览](README.md)的三档口径：**文件存在** / **官方示例描述可运行** / **本机实测通过**。本文绝大多数结论止于前两档；板上推理、延迟和成功率都**还没有实测**。

## 0. 结论速览

| 目标 | 最快的可用路径 | 状态 |
|---|---|---|
| E7 语音识别 | 官方 `ascend-devkit` **Voice 样例**的 WeNet offline encoder `offline_encoder.om`（`Ascend310B1`） | 与官方包 **SHA-256 逐字节一致**；**2026-10-16 板上实测通过**，10 轮文本一致，推理中位 121.0 ms |
| E1 手势识别 | 课程手势包的 `hrnet.om`（4 类 fist/like/ok/palm，`Ascend310B1`，224×224 分类器） | **2026-10-16 板上实测通过**：输出 `[1,4]`、中位 9.07 ms、训练域验证集 **97.9%**（每类 60 张）；但现场四手势仅 71.2%，**fist 被背景干扰判成 palm** |
| 备选/升级 | 语音：昇腾 ModelZoo `ACL_PyTorch` 的 SenseVoice / Paraformer / Zipformer；手势：**YOLOv8n-pose 手部关键点**（HaGRID v1）或 YOLOv10n 手势检测，复用本项目 YOLOv8n→OM 链路 | 官方仓库有转换脚本；两条 YOLO 路线已在别人的 Atlas 200I DK A2（`Ascend310B4`）上跑通，**本机未做** |

一句话：**两个功能都已经有落在本机的官方/课程模型，都已针对 `Ascend310B1` 构建，且已于 2026-10-16 在板上跑通**；缺的只剩「识别率」和「端到端时延」——模型侧耗时已经证明不是瓶颈（语音 121 ms、手势 9 ms）。实测条件与原始数据见[硬件实测](../05-板卡连接与硬件实测.md) 2026-10-16 一节。

## 1. 语音识别（ASR）

**官方 ATC 转换命令**（`ModelConvert/README.md` 与 Notebook 一致，可直接照抄）：

```shell
atc --model=offline_encoder_sim.onnx --framework=5 --output=offline_encoder \
    --input_format=ND --input_shape="speech:1,1478,80;speech_lengths:1" \
    --log=error --soc_version=Ascend310B1
```

`--input_shape` 里 1478 是**编译期固定的最大帧数**，官方推荐的取值有 262/326/390/454/518/582/646/710/774/838/902/966/1028/1284/1478，默认 1478。按 10 ms 帧移，1478 帧约 **14.78 秒**单次音频上限，超长要在前处理里截断。

**模型链与推理契约**（来自官方导出脚本 `export_encoder_onnx.py` 与端侧 Notebook）：

- 权重：WeNet v2.0.1，官方建议 `multi_cn`（`20210815_unified_conformer_exp`）或 wenetspeech 的 checkpoint；导出的是 Conformer **encoder + CTC head + topk beam**，在线/流式部分被关掉（`use_dynamic_chunk=False`）。
- 输入：`speech` `B×T×80` FLOAT32（ND）、`speech_lengths` `B` INT32。
- 输出 5 个：`encoder_out`、`encoder_out_lens`、`ctc_log_probs`、`beam_log_probs`（`B×T×10`）、`beam_log_probs_idx`。
- 前处理：`torchaudio` 读 wav → 重采样 16 kHz → `torchaudio.compliance.kaldi.fbank` 80 维（frame_length 25 ms、frame_shift 10 ms、`dither=0`、波形先乘 `1<<15`，即 `AMPLIFY_FACTOR`）→ padding 到模型 `max_len`。
- 板上推理：`from ais_bench.infer.interface import InferSession`，`InferSession(0, "offline_encoder.om").infer([feats_pad, feats_lengths])`。
- 后处理：**贪心 CTC**——取 `output[1]`（长度）与 `output[4][...,0]`（beam 第 0 路）→ 去重复与 blank（`BLANK_ID = 0`）→ 查 `vocab.txt`。
- **没有独立解码器 OM**：官方样例只做贪心 CTC，不做语言模型重打分。对 E7 的“启动/跳舞/停止”三条固定指令，做关键词/拼音匹配即可，不需要 LM。
- 交互形态：官方样例是**网页前端收麦克风 → 后端消息队列 → 推理 → 文本 → 控制命令**，而不是板上麦克风。这一点正好和项目已有的兜底方案（“无音频硬件时改由开发机收音后经网页接口下发”）一致，也绕开了**板上 USB 音频模块尚未实测**的问题。

结论：本机 om 的 `soc_version` 就是 **`Ascend310B1`**，且用 **CANN 6.2.RC1 aarch64** 工具链构建——与本板（CANN 6.2.RC1）完全对齐。因此它**不是**“来路不明的本地文件”，可以按官方样例对待。但这**不等于板上实测通过**。

**仍然缺一件东西**：官方 v2 目录里的 [`src/E2E-Sample/Voice/v2/wenet/model.py`](https://gitee.com/HUAWEI-ASCEND/ascend-devkit/blob/master/src/E2E-Sample/Voice/v2/wenet/model.py)（样例运行指南要求的结构是 `wenet/{model.py, offline_encoder.om, vocab.txt}`），本机只有 om + vocab + `sample.wav`。补法有两种：取这个 `model.py`，或直接用 Notebook 里的 `WeNetASR` 类（同一套前后处理）。

`ascend/ModelZoo-PyTorch` 的 `ACL_PyTorch` 下有完整的音频类目，都可作为后续升级来源，但**都要自己走 ONNX→ATC**，且 `--soc_version` 要改成 `Ascend310B1`：

- [built-in/audio](https://gitee.com/ascend/ModelZoo-PyTorch/tree/master/ACL_PyTorch/built-in/audio)：`WeNet2_for_Pytorch`（含 `export_onnx_npu.py`、`recognize_om.py`、`static_encoder.sh`、`static_decoder.sh`）、`Paraformer`、`SenseVoice`、`Zipformer`、`Zipformer_streaming`、`whisper`、`whisperx`、`Conformer_for_Pytorch`、`EspNet_for_Pytoch`、`FastSpeech2_for_PyTorch`、`HiFiGAN_for_PyTorch`、`Tacotron2(_dyn)_for_Pytorch`、`CosyVoice(2)`、`LSTM`、`TDNN`、`AASIST-L`、`RawNet2`
- [contrib/audio](https://gitee.com/ascend/ModelZoo-PyTorch/tree/master/ACL_PyTorch/contrib/audio)：`WeNet`、`Whisper`、`SenseVoice`、`Speech-Transformer`、`Deepspeech2`、`wav2vec2`、`data2vec`、`jasper`、`rawnet2`、`tdnn`、`Ecapa_Tdnn`、`FastPitch`、`Tacotron2`、`WaveGlow`
- 模型库条目：[WeNet_Conformer-PyTorch](https://www.hiascend.com/software/modelzoo/models/detail/8ddf64a7b5904fec8bb6b4c92856d118)（语音识别，PyTorch，训练）

注意区分：官方 `ascend/samples` 里的 C++ 样例 [`WAV_to_word`](https://gitee.com/ascend/samples/tree/master/cplusplus/level2_simple_inference/5_nlp/WAV_to_word) 目标硬件是 **Atlas 200 DK / Atlas 300（Ascend310）**，不是 310B，不能直接拿来用。

**语音播报（E7 要求“完成后语音播报”）**：可选 `FastSpeech2 + HiFiGAN`（built-in）或 `Tacotron2 + WaveGlow`（contrib），都要自行转换。对三条固定指令的反馈，**预录音频片段播放**是成本最低、风险最小的做法，TTS 模型作为备选。

## 2. 手势识别

> 本节为结论与落地建议；**逐条证据、候选横向对比与优先级排序**见附件[手势模型调研明细](20-手势模型调研明细.md)。

### 2.1 课程手势包（本机已有，最快落地）

课程任务 3 的手势资料可从课程给出的地址整包下载（[下载链接文件](../../资料/原始解压/软件开发与实训综合实践资料分享/基于计算机视觉的智能机械臂应用实践/AI视觉+语音+机械臂综合实践/任务3_基于手势识别的积木堆叠/手势识别完整代码资料下载链接.txt)）：

`https://staticfile.eduplus.net/dataSet/systemLib/659ef8b7bad34bbe8eb00d2d74c56660.zip`——**2026-10-16 实测 HTTP 200，1,569,889,522 B（1.57 GB）**。本次没有整包下载，而是用 HTTP Range 读取 zip 中央目录（共 53,966 项）+ 取出两个小文件来核对结构。

包内容（目录名做 GBK 解码后）：

```text
任务3_基于手势识别的积木堆叠/
├── 200DK端侧推理/Hand_Gesture/
│   ├── Gesture/val/{fist,like,ok,palm}/*.jpeg
│   ├── hand_gesture_arm.ipynb      9 357 B     ← 端侧推理 + 机械臂动作
│   ├── hand_gesture_test.ipynb   393 246 B
│   └── hrnet.om               46 803 711 B
└── 云端训练/Hand_Gesture/
    ├── Gesture/train|val/{fist,like,ok,palm}/*.jpeg
    ├── hand_gesture.ipynb       43 849 B
    ├── fusion_result.json        3 138 B     ← ATC 图融合日志
    ├── hrnet.om              46 803 711 B
    ├── hrnet.onnx            77 462 516 B
    └── hrnet.pth             77 945 715 B
```

**端侧推理 Notebook 给出的真实契约**（与项目文档里“HRNet 四手势”的说法需要修正）：

- 它不是关键点模型，而是一个 **224×224 的 4 分类器**（网络名沿用 HRNet）。
- 预处理：`transforms.Resize((224,224))` + `ToTensor()`，**没有做归一化**；输入是 RGB。
- 推理：`InferSession(0, 'hrnet.om')` → `model.infer([img])[0]` → `Softmax` → `argmax`；**阈值 0.6**，低于阈值判为“未识别到”。
- 类别顺序：`0=fist(拳头)`、`1=like(喜欢)`、`2=ok`、`3=palm`，并各自映射到一个固定抓取动作。
- 摄像头每 60 帧推理一次；按腕部相机约 7.6 fps 折算，**两次判定间隔约 8 秒**，与 E1 要求的 ≤1.2 s 响应差距很大，必须改推理节拍重做实测。

本机 `资料/展开资源/手势识别训练及转换好的模型/…/hrnet.om`（46,803,711 B）与包内同名文件字节数一致；`strings` 检查只出现 `Ascend310B1`，**没有** `Ascend310` 或 `Ascend310P`——即目标芯片与本板一致。要注意：包内目录写作“200DK端侧推理”，而 OM 实际是 `Ascend310B1` 构建，**以 OM 内的 `soc_version` 为准**。`fusion_result.json` 是 ATC 图融合统计，佐证该 OM 由 ATC 转换产出。

同目录的 `hrnet.onnx` 是**动态 shape**（输入名 `input`，无固定维度），所以输入尺寸只能从 ATC 的 `--input_shape` 或端侧 Notebook 反推；按 Notebook 应为 `1×3×224×224`，**这一点未从 OM 元数据直接读出，属于推断**。

### 2.2 官方 Ascend/samples 手势样例（20 类，Caffe）

[`ascend/samples` → `python/contrib/gesture_recognition_picture`](https://gitee.com/ascend/samples/tree/master/python/contrib/gesture_recognition_picture)：用 `gesture_yuv` 模型对图片做手势识别，是 **20 种手势**的 Caffe ResNet18。

官方 README 直接给出了原始模型与转换命令：

```shell
wget https://obs-9be7.obs.cn-east-2.myhuaweicloud.com/003_Atc_Models/AE/ATC%20Model/gesture_recognition/resnet18_gesture.caffemodel
wget https://obs-9be7.obs.cn-east-2.myhuaweicloud.com/003_Atc_Models/AE/ATC%20Model/gesture_recognition/resnet18_gesture.prototxt
wget https://obs-9be7.obs.cn-east-2.myhuaweicloud.com/003_Atc_Models/AE/ATC%20Model/gesture_recognition/insert_op.cfg
atc --model=./resnet18_gesture.prototxt --weight=./resnet18_gesture.caffemodel --framework=0 \
    --output=gesture_yuv --soc_version=Ascend310 --insert_op_conf=./insert_op.cfg \
    --input_shape="data:1,3,224,224" --input_format=NCHW
```

关键点：**`--soc_version=Ascend310`，要改为 `Ascend310B1` 重转**才能在本板用；硬件要求写的是“已在 Atlas200DK 和 Atlas300 测试通过”。对应 ModelZoo 条目见 `ascend/ModelZoo-TensorFlow` 的 `TensorFlow/contrib/cv/gesture_recognition/ATC_gesture_recognition_Caffe_AE`。类别比 E1 需要的 3 类多，但它是**整图分类**，仍需要先有手部 ROI。

### 2.3 官方板端「模型适配工具」（自训练与自定义手势）

`ascend-devkit` 的 [`src/models_adaption/`](https://gitee.com/HUAWEI-ASCEND/ascend-devkit/tree/master/src/models_adaption) 是本板官方推荐的“训练→导出 ONNX→转 OM”通道，正好补上“拿不到现成 OM 时怎么办”：

- [`classification/mobilenetv3`](https://gitee.com/HUAWEI-ASCEND/ascend-devkit/tree/master/src/models_adaption/classification/mobilenetv3)：含 `train_code` 与 `inference`，适合做自定义手势分类器。
- [`keypoint/AlphaPose_ORB`](https://gitee.com/HUAWEI-ASCEND/ascend-devkit/tree/master/src/models_adaption/keypoint/AlphaPose_ORB)：Labelme 标注 → COCO 关键点格式 → 训练 → `pthtar2onnx.py` 导 ONNX → ATC 转 OM。官方给的转换命令是 `--input_shape="input:1,3,256,192" --soc_version=Ascend310`（同样要改 310B1）。它是 **COCO 17 点人体姿态**（FastPose ResNet50），不是手部关键点；对 E1 里“笑脸触发挥手/点头”这类**身体动作**触发更合适，做手指级手势不合适。
- 另有 `detection`、`segmentation`、`Int8Quant`。

### 2.4 已在 Atlas 200I DK A2 / 310B 上跑通过的 YOLO 手势与手部关键点路径（推荐）

公开渠道里有**两条明确以 310B 为目标、并已上板跑通**的 YOLO 路线。它们的价值在于：本项目**已经有 YOLOv8n → `Ascend310B1` OM 的完整链路**（`scripts/convert_om.sh`，容器内 20 秒），这两条路线的模型族与转换步骤和它几乎重合。

**（1）YOLOv8n-pose 手部关键点（昇腾官方论坛，2025-07-16，板块标签「Atlas 200I DK A2 开发者套件」）**

- 文章：[基于 YOLOv8-Pose 的手部姿态估计实验](https://www.hiascend.com/dev/forum/thread-0279188016799848063-1-1.html)
- 数据集：**HaGRID v1**（同时含手部 bbox 与 21 点关键点；v2 不带关键点），`hagrid_to_yolo.py` 转 YOLO 格式，`kpt_shape: [21, 2]`、单类 `hand`
- 训练：`yolo pose train data=pose.yaml model=yolov8n-pose.pt pretrained=yolov8n-pose.pt epochs=100 imgsz=640 single_cls=true`
- 导出：`yolo export model=best.pt format=onnx imgsz=640`（onnx 1.12.0，opset 17）
- 转换：`atc --model=handpose.onnx --framework=5 --output=handpose --soc_version=Ascend310B4`
- 板上实测（作者数据）：摄像头视频帧 **16–17 FPS**；加 AIPP 后前处理 38 ms → **10 ms**、推理 21 ms → **13 ms**，在 640×640、30 fps 摄像头下达到实时
- 文中给出了完整的前处理（letterbox + 灰条 + BGR→RGB + /255 + HWC→CHW）与后处理（置信度过滤 + NMS + 关键点坐标反变换）代码，以及 AIPP 配置（`RGB888_U8`、`var_reci_chn = 0.003906`）

**（2）HaGRID YOLOv10n 手势检测（《昇腾310B实战》案例 8，2026-10-15）**

- 案例页：[案例 8：实时手势识别](https://zhouxzh.github.io/Ascend310/experiment/case8.html)
- 模型：HaGRID 的 YOLOv10 手势检测权重 `YOLOv10n_gestures.pt`，导出 `--imgsz 640 --batch 1 --opset 13`
- 转换：`SOC_VERSION=Ascend310B4 bash scripts/atc_convert.sh`，OM 静态输入 `1×3×640×640`
- 板端：PyACL 加载 OM + letterbox/RGB/NCHW/归一化，另有 `--benchmark-runs` 的纯 OM 冒烟模式
- 已在其官方 Atlas 板端到端验证，板端软件栈记录为：`npu-smi` 产品标识 **Atlas 200I A2**、芯片 **Ascend 310B4**、Ubuntu 22.04.5、CANN 9.2.0-beta.2、驱动 25.5.0
- 附带一个容易踩的环境坑：官方镜像把摄像头设成 `root:video 0660`，用 `HwHiAiUser` 跑时要先 `sudo usermod -aG video HwHiAiUser` 并重新登录（甚至重插 USB 摄像头）

**关于芯片型号的重要提醒**：上面两条路线用的都是 `--soc_version=Ascend310B4`，而**本项目这块板实测是 `Ascend310B1`**（见[资产清单](09-资产清单.md)）。两者不能互抄签名，转换前必须先在本板确认芯片名（`npu-smi info`，或按官方 ATC 文档用 `ascend-dmi -i -dt` 看 `Chip Name`，去掉空格即为 `soc_version`）。这也解释了为什么 `--soc_version` 在昇腾里是必填且不可猜的参数。

### 2.5 其它候选与需要注意的坑

**手部 ROI 的现成官方件**：[`ascend/samples/python/contrib/hand_detection_Gitee`](https://gitee.com/ascend/samples/tree/master/python/contrib/hand_detection_Gitee) —— TensorFlow **MobileNetV1 + SSD** 人手检测，输入 `image_tensor:1,300,300,3` NHWC UINT8，输出 4 个数组（检测数／类别／置信度／1×10×4 框）；权重 [Hand_detection.pb](https://obs-9be7.obs.cn-east-2.myhuaweicloud.com/003_Atc_Models/AE/ATC%20Model/hand_detection_picture/Hand_detection.pb)（2026-10-16 实测 200，22,475,091 B），原始项目 [victordibia/handtracking](https://github.com/victordibia/handtracking)，**License Apache-2.0**；atc 用 `--framework=3 --soc_version=Ascend310`（同样要改 310B1）。它**只检测手、不分类手势**，正好补上 2.1 那个整图分类器缺的第一级。

**21 点手部关键点**：[`Ascend/mindxsdk-referenceapps` → `contrib/GestureKeypointDetection`](https://github.com/Ascend/mindxsdk-referenceapps/tree/master/contrib/GestureKeypointDetection)（Gitee 上同名目录为空，需用 GitHub）。两级串联：`yolov3_hand.onnx`（手部检测）→ `resnet_50_size-256.onnx`（21 关键点，256×256），**只提供 ONNX**，需自行 ATC；老栈 MindX SDK 2.0.4 + CANN 5.0.4，支持产品写「以昇腾 Atlas310 卡为主要硬件平台」，**未提 310B**。要做真正的手指级关键点，这是目前找到的唯一昇腾方案。

**有现成 OM 但不合用**：[`3Dgesture_recognition`](https://gitee.com/ascend/samples/tree/master/python/contrib/3Dgesture_recognition) 的 ModelZoo 条目确实提供 [3d_gesture_recognition.om](https://obs-9be7.obs.cn-east-2.myhuaweicloud.com/003_Atc_Models/AE/ATC%20Model/3D_gesture_recognition/3d_gesture_recognition.om) 直链（2026-10-16 实测 200，156,463,629 B）——但它是 TensorFlow 3DCNN 的**视频动作**分类（`X:1,16,112,112,3` NDHWC、16 帧、10 类动作），与腕部单帧 640×480 的需求不匹配。

**HaGRID 权重直链（自训练路线的数据与权重来源）**：手势检测 [YOLOv10n_gestures.pt](https://rndml-team-cv.obs.ru-moscow-1.hc.sbercloud.ru/datasets/hagrid_v2/models/YOLOv10n_gestures.pt)（2026-10-16 实测 200，22,442,394 B）；类别含 **fist / like / ok / palm**；数据集与代码仓 [hukenovs/hagrid](https://github.com/hukenovs/hagrid) 为 CC BY-SA 4.0 变体许可——**课设使用前需确认许可条款**。

- **华为 HiLens 手势技能**：官方 HiLens 最佳实践里的 `gesture_recognition_data` 是**给 ModelArts 用的训练示例数据**（类别示例为 Yeah / Rock / OK / Great / Other），要自己训练后在 HiLens 上部署成技能，**不提供可直接用的 OM**；HiLens 设备属 310 系。见[手势识别技能开发（ModelArts+华为HiLens）](https://support.huaweicloud.com/bestpractice-hilens/hilens_06_0004.html)（该域名全站有人机校验，正文未能读取，结论基于搜索片段与社区博文复述）。
- **华为云博客《昇腾 Atlas200DevBoard 开发板部署手势识别 DNN 网络》**（[链接](https://bbs.huaweicloud.com/blogs/387114)）：用 Caffe OpenPose 手部关键点 `pose_iter_102000.caffemodel`，但代码是 OpenCV `readNetFromCaffe`，**实际在板上 CPU 上跑，没有走 NPU**；芯片也是 Ascend310。可以借它的“关键点→手指数”判定思路，**不能把它当作 NPU 手势方案**。
- **MediaPipe**：有把 mediapipe 转 ONNX 后在昇腾 **910A** 上跑的案例（[CSDN](https://blog.csdn.net/qq_57467780/article/details/142630514)），但**没有找到 310B 上的成功案例**；OpenCV Zoo 的 `handpose_estimation_mediapipe` 权重可导出 ONNX，属于“可以试但不保证”的路。
- **自训练方案（最稳）**：要一个带 ROI 的手势方案，最稳妥的是沿用本项目已有的 YOLOv8n → OM 链路，按上面（1）或（2）的数据集与训练命令做，而不是去凑公开的旧 OM。


## 3. `.om` 与芯片的绑定关系（最容易踩的坑）

昇腾官方 ATC 文档对 [`--soc_version`](https://www.hiascend.com/doc_center/source/zh/canncommercial/63RC1/inferapplicationdev/atctool/atctool_000066.html) 的约束是“**请使用与芯片名相对应的 `<soc_version>` 取值进行模型转换，然后再进行推理**”，并且 `Ascend310` 与 `Ascend310P*` 是**不同的取值**。

本次调研里各来源的目标芯片并不相同，正说明这一点：

| 来源 | 给出的 `soc_version` | 能否直接用在 310B1 |
|---|---|---|
| ascend-devkit Voice 样例（语音） | `Ascend310B1` | 可以（本机 om 已核对） |
| 课程手势包 hrnet.om | OM 内为 `Ascend310B1` | 可以 |
| 昇腾论坛 YOLOv8n-pose 手部关键点 | `Ascend310B4` | 同为 310B 系但**签名不同**，按本板实际值改 |
| 《昇腾310B实战》案例 8（YOLOv10 手势） | `Ascend310B4` | 同上 |
| ascend/samples gesture_recognition_picture | `Ascend310` | **不可以**，需重转 |
| ascend-devkit models_adaption/AlphaPose_ORB | `Ascend310` | **不可以**，需重转 |
| ascend/samples WAV_to_word | Atlas 200 DK / Atlas 300 | **不可以**，需重转 |

注意 `Ascend310B1` 与 `Ascend310B4` 同时出现在“Atlas 200I DK A2”这个产品名下（本项目这块板是 `Ascend310B1`，论坛作者与教程作者的是 `Ascend310B4`），所以**不要照抄任何一篇文档里的取值**，每次转换前先在本板查一次芯片名。

好消息是本项目**已经有可用的重转环境**：`scripts/convert_om.sh` 用板卡自带的 CANN 6.2.RC1 aarch64 工具链在 Mac 容器里转，`--soc_version=Ascend310B1`，不需要板卡；四个坑（Python 3.10 的 `collections.Iterable`、numpy 2.x 的 `np.float_`、缺 `libascend_hal.so`、缺 `libxml2`）已经解决。也就是说：**只要能拿到 ONNX/Caffe 原始模型，就能自己产出本板的 OM。**

## 4. 对 E1 / E7 的落地建议

**E7 语音控制（启动 / 跳舞 / 停止）**

1. 取官方 `e2e_voice_lamp.zip`，在板上用 `InferSession` + `offline_encoder.om` + `vocab.txt` 先跑通包内 `sample.wav`，与官方 Notebook 的预期输出对齐。这是**最低成本、最有把握的第一条验收**。
2. 指令识别不要接语言模型：对贪心 CTC 输出做“启动/跳舞/停止”的文本或拼音关键词匹配，加去抖与冷却（项目[日志契约](18-日志契约.md)里的 `interaction` 事件已有 `source`/`command`/`confidence` 字段）。
3. 收音形态优先跟官方走（网页/开发机收音 → HTTP 下发），既避开未实测的板载 USB 音频，也与项目既定的“控制指令 JSON + `source` 字段”契约一致。
4. 注意 14.78 秒静态上限与 padding/截断逻辑；指令级录音足够，但要固化录音时长。
5. 语音播报先用预录音频片段，TTS 模型（FastSpeech2+HiFiGAN）留作备选。

**E1 手势+表情交互（≥3 类，≥80%，≤1.2 s）**

1. 先用课程 `hrnet.om` 跑通板上推理，确认四类映射与 0.6 阈值；它自带训练/验证集，可先离线算混淆矩阵。
2. **补齐手部 ROI**：该模型是整图 224×224 分类器，腕部相机画面里包含桌面、物块和机械臂。要么固定“手势观察位 + 画面裁剪”，要么用项目已有 YOLOv8n 链路训一个手部检测器，或直接用官方的 [hand_detection_Gitee](https://gitee.com/ascend/samples/tree/master/python/contrib/hand_detection_Gitee)（Apache-2.0）。
3. **响应时延要重新设计**：课程 Notebook 每 60 帧推理一次（≈8 s 一次判定），而 E1 要求 ≤1.2 s。腕部相机只有约 7.6 fps，必须改成**逐帧或每 2–3 帧推理 + 连续 N 帧一致才确认**，并把实测延迟写进验收记录。
4. 「笑脸触发」需要一个表情分支，本次调研**没有找到**本板可用的现成笑脸 OM；可用官方 `models_adaption/classification/mobilenetv3` 自训练，或先用 AlphaPose 的身体动作（挥手/点头）替代。
5. 若课程 4 类在真实光照下的准确率不达标，走**第 2.4 节**的两条已验证路径：**YOLOv8n-pose 手部关键点**（HaGRID v1，21 点，可直接按“手指数/手指伸展组合”判手势，比四分类泛化更好）或 **YOLOv10n 手势检测**。两者都能复用本项目已有的 YOLOv8n→OM 转换链路，是本项目成本最低的“自训练”方案。
6. 摄像头权限：官方镜像把 `/dev/video0` 设为 `root:video 0660`，如果板上用非 root 用户跑，先 `sudo usermod -aG video <user>` 并重新登录（必要时要重插 USB 摄像头）。这是《昇腾310B实战》案例 8 记录的坑。

## 5. 已实测、未核实与风险

**2026-10-16 已在本板上实测通过的部分**（条件与原始数据见[硬件实测](../05-板卡连接与硬件实测.md)）：

- 两个 OM 都能加载并推理。语音 `offline_encoder.om` 10 轮文本完全一致（中位 121.0 ms/句，10.24 s 音频）；手势 `hrnet.om` 输出 `[1,4]`，中位 9.07 ms/帧，与 ONNX 的 argmax 在合成与真实图像上都一致（`max_abs_diff` 0.0014 / 0.0009）。
- `hrnet.om` 的**输入规格已由 OM 描述确认**为 `input [1,3,224,224]` float32、输出 `output [1,4]` float32——原先靠 Notebook 反推的推断已不必要。
- 两个模型先后驻留无内存问题（板端显存 619/3513 MB，语音 78.5 MB + 手势 46.8 MB）。

**仍未核实**：

- **识别率**：语音只跑了官方那一段样例（无第二段音频可测）。手势已测：训练域验证集 **97.9%**，现场四手势 **71.2%**——后者是单会话、真值宽松的数字，**不能当准确率**，需要多会话 + 逐帧标注重测。
- **手势在腕部相机取景下的表现**：已确认**背景是主因**（80% 中心裁剪把合计从 71.2% 提到 92.1%），但仍缺手部 ROI；固定裁剪对不同手势敏感度不同（`like` 在 ≤70% 崩、`ok` 在 ≤50% 崩）。
- **端到端时延**：不含收音、去抖、指令匹配（E7）与 ROI 裁剪、多帧确认（E1）。
- **板上音频硬件未实测**：课程资料描述有 USB 音频模块，本机没测过；官方样例走的是网页收音，不构成板上音频可用性的证据。
- **长跑的热与内存稳定性**：本次是短时推理。
- **课程手势包未整包下载**：1.57 GB，本次只用 Range 读了中央目录和两个小文件，训练集规模与质量未评估。
- **`vocab.txt` 覆盖范围未验证**：WeNet `multi_cn` 词表对“启动/跳舞/停止”的识别表现要实测。
- **未找到**本板可用的现成「笑脸/表情」OM；也**没有找到**任何“下载即用、面向 310B”的现成手部关键点 OM——该方向目前只有“按数据集自训练”的已验证路径（第 2.4 节）。
- **未上板验证的第三方结论**：论坛 YOLOv8n-pose 文的 16–17 FPS、AIPP 前后的 38→10 ms / 21→13 ms，以及《昇腾310B实战》案例 8 的端到端结果，都是**别人在他自己的板子上**（`Ascend310B4`，案例 8 的软件栈为 CANN 9.2.0-beta.2）得到的，不是本项目的实测数字，引用时必须带这个前提。
- **HaGRID 数据集许可与规模**未核对；用于课设前要确认许可证与数据量（v1 全量很大，实训建议用低分辨率子集）。
