需求：≥3 类手势、成功率 ≥80%、指令响应 ≤1.2s、腕部 USB 单目 640×480 @ ~7.6fps

证据分级标注：**[官方文档]** / **[仓库有文件]** / **[仅社区帖子]** / **[未验证]**。

> 本文是[语音与手势模型调研](19-语音与手势模型调研.md)的**手势侧明细附件**：那份给出语音+手势的合并结论与落地建议，本文保留逐条证据、候选横向对比与优先级排序。
>
> **2026-10-16 复核更正（重要）**：本文初稿把本机 `hrnet.onnx` / `hrnet.pth` 判为 **64 类**，**这是错的，实际是 4 类**。初稿用 initializer 字节数（32768 B）反推维度时算错：`32768 B ÷ 4 B = 8192` 个 float，即 `4×2048`；而 **`512×64` 是 32768 个元素＝131072 B**，与实测字节数不符。三种独立测量一致，见 §7.2。因此「需要向课程方索取 64 类标签表」的说法作废——标签表已由课程端侧 Notebook 给出。

## 4. HiLens `gesture_recognition_data` 能否用于 Atlas 200I DK A2

- **[仅搜索片段，正文未验证]** 华为 HiLens 最佳实践《手势识别技能开发（ModelArts+华为HiLens）》写明："华为 HiLens 在公共 **OBS 桶**中提供了手势识别技能的**用于模型训练的示例数据**，命名为 `gesture_recognition_data`"。
  <https://support.huaweicloud.com/bestpractice-hilens/hilens_06_0004.html>（**该域名全站被 "Security Verification" 人机校验拦截，playwright/jina/http 三路均失败，我未能读到正文**）
- 另一篇华为云社区博文复述了同一数据集的**类别**：`Yeah、Rock、OK、Great、Other`（5 类），并说明流程是"下载 `gesture_recognition_data.zip` → 上传 OBS → ModelArts 自动学习/训练 → 部署为技能"。**[仅社区帖子]**
  <https://bbs.huaweicloud.com/blogs/414915> ｜ <https://bbs.huaweicloud.com/blogs/415112>
- **结论（据现有证据）**：`gesture_recognition_data` 是**训练数据集（zip）**，**不是可下载的 `.om` 技能模型**；技能模型需在 ModelArts 上自行训练生成，产物面向 **HiLens Kit** 系列硬件。**没有找到任何 "HiLens 手势 om 下载" 的证据**，也**没有找到 HiLens 技能可部署到 Atlas 200I DK A2 的官方说明**。→ 判为 **[未验证 / 大概率不适用]**。
- 搜过的关键词：`HiLens gesture_recognition_data 手势技能 模型下载 Atlas 200I DK A2`、`HiLens gesture_recognition_data OBS 下载 手势识别技能 模型 训练数据集 obs 桶 地址`。

## 5. 可自行转换的候选（ONNX/PyTorch → atc → Ascend310B1 的 om）

### 候选 A：⭐ HaGRID + YOLOv10（**强烈推荐**）

- **权重来源（直链，官方 README 提供）**：
  - 手势检测 `YOLOv10n_gestures.pt`（mAP **88.2**）：`https://rndml-team-cv.obs.ru-moscow-1.hc.sbercloud.ru/datasets/hagrid_v2/models/YOLOv10n_gestures.pt`
  - 手势检测 `YOLOv10x_gestures.pt`（mAP 89.4）／手部检测 `YOLOv10n_hands.pt`（mAP 87.9）／全帧分类器 `ResNet18.pth`（F1 **98.3**）、`MobileNetV3_large.pth`（93.4）、`ConvNeXt_base.pth`（96.4）
  - 证据：<https://raw.githubusercontent.com/hukenovs/hagrid/master/README.md>
- **类别覆盖**：HaGRID 明确包含 **`fist`、`like`、`ok`、`palm`**，另有 `peace / stop / call / dislike / four / mute / one / three / two_up / rock / point …`。→ **直接满足"≥3 类"且与项目现有四手势命名一致**。**[官方文档]**
- **许可证**：数据集 **CC BY-SA 4.0 变体**（README "License" 段 + `license/en_us.pdf`）；代码仓 `hukenovs/hagrid` 亦为 CC BY-SA 4.0 变体。HaGRIDv2 = 1,086,158 张图 / **33 类** + `no_gesture`。**[官方文档]**
- **ONNX 导出可行性**：**已验证**。社区案例给出导出脚本与 atc 命令：
  ```
  python weights/export_yolo_to_onnx.py --weights weights/YOLOv10n_gestures.pt \
      --output-dir models --imgsz 640 --batch 1 --opset 13 --device cpu
  SOC_VERSION=Ascend310B4 bash scripts/atc_convert.sh
  ```
  该案例**已在官方 Atlas 开发板端到端验证通过**（板端记录：产品 `Atlas 200I A2`、芯片 **Ascend 310B4**、Ubuntu 22.04.5、固件 7.8.0.5.216、驱动 25.5.0、**CANN 9.2.0-beta.2**）。模型输入固定 `1×3×640×640`，letterbox 预处理，输出经置信度过滤 + 坐标恢复 + NMS。**[仅社区帖子，但含实测参数]**
  <https://zhouxzh.github.io/Ascend310/experiment/case8.html>
- **算子坑**：① 该案例用的是 **CANN 9.2.0-beta.2**，本机是 **CANN 6.2.RC1**，YOLOv10 的 `DFL`/`TopK`/`NonMaxSuppression` 等算子在 6.2.RC1 上支持情况未验证，建议先在 6.2.RC1 上跑一次 atc 试转（`--soc_version=Ascend310B1`），失败则改在 640→320 降分辨率或换 YOLOv8 系导出；② 640×640 输入对 3.5GB 内存/AICore 是负担，若帧率不够可换 `--imgsz 320`（精度需重测）；③ 类别顺序必须以导出的 meta 为准。
- 若只需要"分类"不要"检测"，**HaGRID 全帧分类器 ResNet18（F1 98.3）** 是最轻的路线，ONNX 导出无特殊算子。

### 候选 B：MediaPipe Hands（palm detection + hand landmark）

- **权重来源/格式**：官方为 **`.tflite`**，模型包 = `palm detection`（**192×192**）+ `hand landmark`（**224×224**），float16 量化。**[官方文档]**
  <https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker>
- **ONNX 导出可行性**：**有公开可行的转换路径** —— `tf2onnx` 直接转，且已有第三方教程给出完整命令（Renesas RZ/V2H 文档）：
  ```
  python -m tf2onnx.convert --tflite hand_landmark_full.tflite --opset 12 \
      --output hand_landmark_full.onnx --inputs-as-nchw input_1
  python -m tf2onnx.convert --tflite palm_detection_full.tflite --opset 12 \
      --output palm_detection_full.onnx --inputs-as-nchw input_1
  ```
  **[仅社区/第三方文档]** <https://renesas-rdk.github.io/rzv2h_rdk_documentation/latest/chapter-3/drp_ai/model_compilation_tutorials/tutorial_media_pipe_hand_landmark.html>
- 另有社区已预转的 ONNX：`opencv/palm_detection_mediapipe`（OpenCV Zoo）。<https://huggingface.co/opencv/palm_detection_mediapipe>
- **许可证**：MediaPipe 为 Apache-2.0（模型卡随官方发布）。
- **算子坑（重要）**：palm detection 的 TFLite/ONNX 转换后输出被社区反复讨论为 `[2016, 18]` / `[2016, 1]` 形式（anchors 维度），**后处理需自行实现**，且 tflite→onnx 的 `--inputs-as-nchw` 会引入额外 Transpose；`tf2onnx` 产出的算子（如 `Resize`/`Squeeze`/自定义 anchor decode）在 CANN 6.2.RC1 上是否全部支持**未验证**。整体踩坑成本高于候选 A。
- 参考讨论：<https://github.com/google-ai-edge/mediapipe/issues/5966>

### 候选 C：handpose_x（ResNet50 手部 21 关键点）

- 权重来源：见 §3.1 的 `resnet_50_size-256.onnx`（obs 直链），原始项目 <https://github.com/XIAN-HHappy/handpose_x>。参考实现为 CSDN codechina（现已跳转），**镜像可用性需再确认**。
- 输入 **256×256**（aipp `src_image_size_w/h: 256`）；输出为关键点热图 + 关联度两路。
- **不直接输出手势类别**，需在 21 关键点上加判据。可作为"要做手部关键点"时的首选。

### 候选 D：官方 gesture_recognition（Caffe ResNet18，20 类）

- 见 §1.1。轻量（224×224 ResNet18）、有 `insert_op.cfg` 做 aipp 预处理、有现成 obs 权重，**转换链路官方已写清**。缺点是**未在 310B 验证**、类别集未必覆盖项目四手势、且是 Caffe 老框架。

### 候选 E：mmpose HRNet 人体关键点（社区实测 310B1）

- 社区贴给出**在 `davinci-mini`（= 本项目同类 310B 板）上成功转换的 atc 命令**：
  `atc --model=end2end.onnx --framework=5 --output=end2end --input_format=NCHW --input_shape="input:1,3,256,256" --log=error --soc_version=Ascend310B1` → `ATC run success`。**[仅社区帖子]**
  <https://cfanz.cn/resource/detail/OkjWlognoQVGl>
- 这是**人体**关键点（20 骨架连接），非手部，但证明了 **256×256 ONNX 在 310B1 上转 om 可行**。

## 6. `.om` 的芯片兼容性

**结论：`.om` 与目标芯片型号强绑定，不能跨 Ascend310 / 310P / 310B 直接复用。** 证据链：

1. **[官方文档]** ATC 工具 `--soc_version` 参数说明页明确：
   > "参数值约束：请使用与芯片名相对应的 `soc_version` 取值进行模型转换，然后再进行推理。"
   > "昇腾310B AI 处理器参数值：`Ascend310B*`…… 昇腾310B AI 处理器使用示例：`--soc_version=Ascend310B1`"
   <https://www.hiascend.com/doc_center/source/zh/canncommercial/62RC2/inferapplicationdev/atctool/atctool_000066.html>
   （同页另一版本列举 `Ascend310` / `Ascend310P*` / `Ascend910*`，并说明可通过 `npu-smi info` 的 Name 前加 `Ascend` 得到取值。）
2. **[官方文档]** Atlas 200I DK A2 开发者套件的《在开发者套件上转换模型》页给出 `--soc_version` 参数与 `--framework`（0:Caffe / 1:MindSpore / 3:TensorFlow / 5:ONNX）说明。
   <https://www.hiascend.com/document/detail/zh/Atlas200IDKA2DeveloperKit/latest/Application%20Development%20Guide/tmuacop/tmuacop_0025.html>
3. **[仓库有文件]** AlphaPose README 两次写明"**在310B芯片上进行转换，修改参数 `--soc_version=Ascend310B1` 即可**"——即同一份 pb/onnx 需要**为不同芯片重新 atc**，om 不复用。
   <https://gitee.com/ascend/ascend_community_projects/raw/master/AlphaPose/README.md>
4. **[官方文档]** 官方 Atlas 200I DK A2 机械臂例程中，`dofbot_garbage_yolov5/model/` 与 `dofbot_color_stacking/scripts/model/` 里放的是 **`yolov5s_bs1.om`**（板端随包交付），说明官方在 A2 上使用**为该芯片生成的 om**。
   <https://www.hiascend.com/document/detail/zh/Atlas200IDKA2DeveloperKit/23.0.RC2/Application%20Cases/raadg/raadg_0012.html>
5. **[仅社区帖子]** 现成的官方/社区手势 om（如 §1.2 的 `3d_gesture_recognition.om`、`gesture_recognition_picture` 的转换命令）**一律是 `--soc_version=Ascend310`（Atlas 200 DK / Atlas 300）**；AlphaPose 的 onnx→om 也是 `Ascend310`。→ **网上能直接下到的手势 om 基本都是 Ascend310 版，A2/310B1 上需要重新转换。**

**推论（明确标注为推论）**：即便同为 310B 家族，`Ascend310B1` / `Ascend310B4` 等细分取值也应各自转换（社区案例在 310B4 上用 `Ascend310B4`，本项目是 `Ascend310B1`）。**[未验证：我没有在板上实测跨 soc_version 加载失败的具体报错码]**；Ascend 论坛有一条"加载模型报错 500002"的帖子可作为佐证线索但未读取正文：<https://www.hiascend.com/forum/thread-0296166331718266158-1-1.html>

### 7.2 我从文件本身读出的规格（不是推测）

直接解析 `hrnet.onnx`（protobuf 手写遍历）与 `hrnet.pth`（zip + `pickle` 解析 `archive/data.pkl`，不执行任意代码）：

| 测量 | `hrnet.onnx` | `hrnet.pth` |
|---|---|---|
| `classifier.weight` | initializer `dims=[4, 2048]`，`raw_data` 长度 **32768 B**（＝4×2048×4） | `size=(4, 2048)` |
| `classifier.bias` | initializer `dims=[4]`，`raw_data` 长度 **16 B**（＝4×4） | `size=(4,)` |

- **结论：这是 4 类分类器**，输入名 `input`、输出名 `output`。三条独立证据互相印证：① ONNX initializer 的显式 `dims`；② `raw_data` 实际字节数（32768 B 与 16 B 只能分别是 8192 个和 4 个 float32）；③ `.pth` 里同名张量的 `size`。
- **旁证**：课程手势包里 `Gesture/{train,val}/` 下**正好只有 `fist`/`like`/`ok`/`palm` 四个类目录**；端侧 Notebook `hand_gesture_arm.ipynb` 对输出做 `Softmax` 后取 `argmax`，并把 `y_pred == 0/1/2/3` 分别映射到拳头/喜欢/ok/palm，阈值 0.6。→ **标签表就是 `0=fist, 1=like, 2=ok, 3=palm`**，不需要向课程方再索取。
- **图输入/输出的 shape 未写进 ONNX**：`graph.input` / `graph.output` 的 `ValueInfoProto` 里只有 `elem_type=FLOAT`，**没有 dim 字段**（动态 shape）。因此 `1×3×224×224` 这个尺寸**不是**从 ONNX 读出来的，而是来自课程端侧 Notebook 的 `transforms.Resize((224,224))`；转换时必须用 atc 的 `--input_shape` 固化。

## 推荐优先级

**P0 —— HaGRID 全帧分类器（ResNet18 / MobileNetV3_large）或 HaGRID YOLOv10n 手势检测 → atc 转 `Ascend310B1` om。**
理由：① **类别直接覆盖 fist/like/ok/palm**（HaGRID 官方类表）；② 权重**直链可下**、许可证明确（CC BY-SA 4.0 变体）；③ **已有社区在 Atlas 310B 上对该数据集模型完成端到端 ATC + OM + 摄像头实测**，路径被验证过；④ 224×224 分类或 320/640 检测都在 310B1 能力范围内，最易满足"≤1.2s / ≥80%"。风险：CANN 6.2.RC1 与案例所用 9.2.0-beta.2 的算子差异，需先试转。

**P1 —— 复用本机 `hrnet.om`（4 类，fist/like/ok/palm）。**
理由：零训练成本、模型已在手、224×224 极轻，**该 om 就是 `Ascend310B1` 构建**（无需重转）。
**2026-10-16 已在板上量过**：训练域验证集（课程自带 `val/`，每类 60 张）**97.9%**，标签顺序确认为 `0=fist 1=like 2=ok 3=palm`；但**现场四手势只有 71.2%**——`fist` 因逆光窗与走动的人等背景被判成 `palm`，做 80% 中心裁剪后合计回到 92.1%（`fist` 5.9%→77.2%）。结论：**模型本身够用，卡在取景与背景**，下一步是接手部 ROI 而不是换模型。
课程 Notebook 的「每 60 帧推理一次」节拍仍对不上 ≤1.2 s（详见[19 号文档](19-语音与手势模型调研.md)第 4 节）。

**P2 —— mindxsdk-referenceapps `GestureKeypointDetection`（yolov3_hand.onnx + resnet_50_size-256.onnx）+ 自写关键点规则分类。**
理由：真正的"手部关键点"方案，能满足"手部关键点识别"这一半需求。代价：老栈（MindX SDK 2.0.4 / CANN 5.0.4）、两模型串联延迟翻倍、分类逻辑要自己写，且未在 310B 验证。

**P3 —— 官方 `gesture_recognition_picture`（Caffe ResNet18 20 类）。**
理由：转换链路官方文档化、有 aipp 配置。代价：Caffe 老框架、20 类未必含项目手势、只在 200DK/300 验证过。

**P4 —— MediaPipe Hands。**
理由：手部关键点精度最好、Apache-2.0。代价：tflite→onnx 后处理要自己重写、`[2016,18]` 锚框解码复杂、算子兼容性未验证——**作为最后手段**。

**P5 —— AlphaPose / OpenPose / DEKR / HRNet(pose_estimation) / HiLens gesture_recognition_data。**
理由：前四者是**人体**关键点（不含手），HiLens 的 `gesture_recognition_data` 只是训练数据且面向 HiLens Kit。**不建议作为手势控制的主路径**。
