## 结论

| 目标 | 当前程度 | 判断 |
|---|---|---|
| 摄像头解析/物体识别函数 | 有完整教学链路：取帧、预处理、OM 推理、NMS、框坐标还原和标签 | **可以抽取成旧 YOLOv5 OM 的二维检测原型**，但尚不是稳定模块 |
| 机械臂操作模块 | 有 `Arm_Lib` 调用面、固定姿态、夹爪动作、关节读写和动作学习示例 | **可以包装成设备适配器和固定动作原型**，不能直接安全运行或完成任意位置抓取 |
| 识别后空间抓取 | 检测框中心只用于画图，动作始终抓固定位置 `p_a` | **参数不足**；缺相机标定、坐标变换、抓取点、关节配置和结果验证 |
| ROS/ROS2 入口 | 只有环境名 `ros-arm-env` 和依赖 KDL/kdl_parser 的运动学头文件 | **不存在项目级入口**；没有 ROS 包、节点、launch、topic/service/action 或构建清单 |

因此，现有资料能组成“相机二维识别”和“固定点关节动作”两个受限原型，不能直接组成“识别任意物体位置并抓取”的闭环系统。

## 当前实际调用链

来源为 `资料/展开资源/arm_line2/arm_line2/Clamping_block.ipynb` 的单个顶层代码单元：

```text
camera()
  -> VideoCapture(0) / 每 10 帧处理一次
  -> garbage_identify.garbage_run(frame)
  -> infer_image(frame, model, labels, cfg)
  -> preprocess_image: 640x640 letterbox, BGR->RGB, HWC->CHW, float16 / 255
  -> InferSession(0, yolov5s_bs1.om).infer([img])[0]
  -> NMS(conf=0.7, iou=0.7)
  -> Nx6 [x1, y1, x2, y2, confidence, class_id]
  -> get_pos() 仅返回标签名称列表
  -> 同一列表首项连续出现 3 次
  -> Blue/Yellow/Red 分支调用固定关节角抓放
```

这个链路没有把像素中心传给机械臂，也没有计算 `camera -> base -> tool` 的坐标关系。标签文件有 `Blue/Green/Red/Yellow`，但绿色没有动作分支。

## 已有参数清单

### 摄像头与识别

| 参数 | 当前值/来源 | 是否足以直接固化 |
|---|---|---|
| 摄像头索引 | `0` | 否；需按实际设备稳定 ID 配置 |
| 采集处理尺寸 | `640 x 480` | 可作为原型默认值；实际分辨率、帧率和畸变待测 |
| 模型输入 | `640 x 640` | 仅源码假定；需核对 OM 实际输入 shape |
| 输入格式 | BGR 转 RGB、CHW、`float16`、除以 255 | 可复用，但缺 batch 维约定和模型元数据验证 |
| 推理设备 | `InferSession(0, ...)` | 设备 0 是示例值，需配置化 |
| 模型/标签 | `yolov5s_bs1.om`、`coco_names.txt` | 文件存在；标签实为四种颜色，不是 COCO 80 类 |
| 置信度/NMS IoU | `0.7 / 0.7` | 有初值，无验证集调参依据 |
| 检测输出 | `Nx6: xyxy, confidence, class_id` | 可定义为适配器输出，但须绑定该模型真实张量布局 |
| 取样节奏 | 每 10 帧推理 | 有示例值，无实时性或延迟验收依据 |
| 稳定触发 | 列表首项同名连续 3 次 | 不足；多目标时缺 `track_id`、空间稳定和超时 |
| 所谓预热 | 前 5 次调用直接跳过推理 | 不是实际模型预热，应删除或改为真实 warm-up |

### 机械臂与动作

| 参数 | 当前值/来源 | 风险/缺口 |
|---|---|---|
| 舵机编号 | `1..6`，6 号作为夹爪 | 5 个机身关节与夹爪的轴向、方向、零位待确认 |
| 单关节写入 | `Arm_serial_servo_write(id, angle, time_ms)` | 未知 ACK、超时、错误码和运动完成语义 |
| 六关节写入 | `Arm_serial_servo_write6(..., time_ms)` | 未知是否同步、是否检查限位 |
| 关节读取 | `Arm_serial_servo_read(id)` | 有调用示例，失败返回值和刷新率未知 |
| 夹爪 | 60°张开、135°闭合、400 ms | 无力/接触/夹持成功反馈，角度需实物标定 |
| 普通移动 | 默认 500 ms；5 号舵机时间乘 1.2；关节逐个下发间隔 10 ms | 只适合复现教学动作，不能当轨迹执行器 |
| 固定姿态 | `p_mould/p_top/p_right/p_a/p_b/p_c/p_d` | 两份 Notebook 的部分值冲突，且出现 200°/220°/270° |
| FK/IK | `dofbot_getFK`、`dofbot_getIK` | 需要 URDF；当前没有 URDF、单位/关节顺序/ABI说明和 Python 绑定 |
| 停止 | 动作组有 `Arm_Action_Mode(0)` | 不能据此推定通用急停或在途运动停止能力 |

课程称部分舵机为 0–180°、5 号可到 270°，而流水线姿态又让 1 号到 200°/220°。在实际 SDK、固件、接线和限位核对前，不能把这些数值合并成可直接运行的统一配置。

## 要形成可调用模块，还缺什么

### 1. 可先抽取的纯感知函数

建议契约：

```python
detect(frame_bgr, model, config) -> list[Detection2D]
```

`Detection2D` 至少包含 `frame_id/timestamp/model_version/class_id/label/confidence/bbox_xyxy_px`，可选 `center_px/track_id`。该函数只做预处理、推理和后处理，不打开摄像头、不操作 UI、不调用机械臂。现有 `letterbox`、`preprocess_image`、`infer_image` 和 NMS 可以作为来源，但需补模型 I/O 固定样本测试、空结果/断流处理、日志和显式异常。

### 2. 可先抽取的机械臂设备适配器

建议最小接口：

```text
connect / close
read_joint_state
move_joints(command_id, joint_targets, duration_ms)
set_gripper(command_id, target)
stop_if_supported
```

适配器负责 SDK 单位、舵机映射、限位、超时和原始反馈，不内置“蓝色去 B 点”这样的业务规则。固定姿态只能放在经过现场确认的版本化设备配置中，不能继续作为 Notebook 全局变量。

### 3. 任意位置抓取的关键缺参

- 相机内参 `K`、畸变参数、分辨率对应关系和相机安装方式；
- 外置相机的 `T_base_camera`，或眼在手上的 `T_tool_camera` 与时间同步；
- 没有深度时的桌面平面/单应性、尺度、有效区域和物体高度误差；有深度时的深度配准与有效值规则；
- 机械臂关节树、轴向、零位、方向、软硬限位、连杆单位、工具中心点和夹爪几何；
- 检测中心到抓取接触点/姿态的计算、接近与抬升偏移、投放区域；
- IK 可达性、碰撞/线缆约束、速度限制、取消与失败恢复；
- 到位、夹住、移除原位和投放成功的反馈证据。

这些参数没有补齐前，`bbox center -> joint angle` 不能可靠计算。

## ROS/ROS2 入口核对

当前工作区未找到以下任何项目文件或代码入口：

- `package.xml`、`CMakeLists.txt`、ROS Python 包 `setup.py/setup.cfg`；
- `*.launch.py`、`*.launch`、URDF/Xacro、RViz 配置；
- `rclpy/rospy` 节点初始化；
- publisher/subscriber、topic、service、action 定义；
- MoveIt 配置或可直接启动的 ROS 工作区。

`ros-arm-env` 只是课程环境名称，不能证明 ROS2 已安装；`dofbot_kinemarics.h` 使用 KDL 与 `kdl_parser`，只能说明运动学库面向 ROS 生态依赖，不能作为 node 或 launch 入口。

如果后续确认采用 ROS2，最小入口建议拆成：

```text
camera_node -> /camera/image_raw
detector_node -> /detections_2d
localization_node -> /objects_3d + TF(base/camera/tool)
arm_driver_node -> /joint_states + FollowJointTrajectory 或受控 action
task_coordinator -> PickPlace action + ExecutionStatus
```

这是建议架构，不是当前已存在实现。第一阶段也可以先用进程内 Python 接口做离线识别测试；是否引入 ROS2 应在确认目标板环境、SDK线程/进程边界和后续 MoveIt/TF 需求后决定。

## 推荐实施顺序

1. 从开发板只读确认 `Arm_Lib`、CANN/ais_bench、OM 输入输出、相机设备和 ROS2 包清单。
2. 抽取纯 `detect()`，用录制图像验证四类标签、坐标还原、空结果和异常路径，全程不导入 `Arm_Lib`。
3. 建立机械臂设备配置与适配器，先只读关节；人工确认限位后才允许低速单关节测试。
4. 完成相机标定和桌面平面定位，输出带误差与标定版本的基座坐标。
5. 接入 IK/可达性与单目标抓放，再加入结果验证、取消和互斥。
6. 最后决定是否以 ROS2 node/topic/action 封装；若采用 ROS2，再补包清单、launch、TF、URDF 和硬件驱动入口。
